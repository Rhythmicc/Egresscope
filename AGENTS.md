# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Egresscope product decisions

- This is a new, independent product. Do not reuse the legacy sub-surge Web UI or CLI.
- The first screen after login is the operations dashboard, based on `design/option-1-dashboard.png`.
- Device drill-down uses the dark flow-observability direction in `design/option-2-device-flow.png` to explain source device → matched rule → strategy groups → exit node.
- Traffic auditing must expose source device/IP, active connections, per-device upload/download rate, matched rule, complete strategy chain, and per-chain usage.
- Strategy presentation prioritizes 节点选择, 手动选择, and regional families (for example 美国 → 美国最佳 → 美国均衡). Secondary rule policies stay collapsed by default.
- Only mihomo `Selector` groups are editable. `URLTest`, `LoadBalance`, and `Fallback` groups are shown as explicit read-only automatic modes; the API rejects manual writes to them with a specific explanation.
- Regional strategy cards separate the editable exit mode from automatic-mode behavior and node observability. Show each member's latest mihomo delay, availability, and URLTest winner; represent load-balance latency as a range instead of a misleading single best value.
- The strategy and node workspace uses collapsible, high-density proxy groups with directly selectable member cards, an unmistakable selected state, search, group health summaries, and a separate read-only node-health layer for automatic strategies. Keep individual node cards compact—no large blank card bodies or oversized padding—and fit substantially more nodes per row than ordinary dashboard cards. It should exceed yacd's scanability while preserving SSSLab Proxy's hierarchy and light/dark themes.
- Preserve provider-supplied country/region flag emoji in node labels. When a node name has no flag, infer a display-only flag from common region names or airport/location tokens; never rewrite the mihomo node ID used by strategy APIs.
- Light, dark, and system theme modes are required.
- The production Web port is 2086. TLS termination is external and is not part of this repository.
- All Web-visible timestamps and day boundaries use `Asia/Shanghai`, independent of the NAS or container host timezone.
- Request rules are a first-class workspace, separate from node subscriptions and policy-group membership. Preserve rule-set identity, source, order, target policy, enabled state, and refresh interval; custom one-off rules are an explicit override layer.
- Subscription records are owner-scoped and persisted in SQLite. URLs are treated as credentials and never returned in plaintext; each subscription has a revocable tokenized Mihomo provider URL. Only an administrator may choose the single active gateway node source, and refreshing it replaces node inventory without replacing rule order or policy topology.
- Subscription SSRF validation must distinguish mihomo Fake-IP answers from real private targets. Keep private, loopback, link-local, and reserved destinations blocked; when the host resolver returns a Fake-IP, require a successful public DNS-over-HTTPS A/AAAA recheck before downloading or following a redirect.
- Each owner-scoped subscription exposes two revocable client-profile links in the Web UI: a complete Surge managed configuration and a complete Clash/Mihomo YAML configuration. Keep gateway-only TUN, controller, LAN listener, and authentication settings out of these client deliveries; generated profiles include the subscription's nodes plus portable regional strategies and safe baseline rules.
- Import the legacy sub-surge rule-set catalog as data only. Do not reuse its Web UI, CLI, or eager rule-expansion implementation; compile the catalog to mihomo `rule-providers` and ordered `RULE-SET` references.
- Dashboard and audit statistics must survive panel restarts. Persist core counters, connection cursors, sample intervals, device/chain rollups, and detail samples in SQLite while enforcing the viewer device scope in historical queries.
- The device inventory merges live connections with retained audit history. Treat explicit HTTP/SOCKS proxy source IPs as first-class devices alongside transparent LAN gateway clients, while preserving viewer device scoping.
- Keep mihomo and Docker infrastructure source addresses out of end-device rankings, inventories, and selectors. Their traffic still contributes to gateway-wide totals; configure exact exclusions with `SSSLAB_INFRASTRUCTURE_SOURCE_IPS` rather than hiding broad private subnets.
- Dashboard throughput periods are functional data queries, not cosmetic tabs: live uses a 15-minute/10-second view, while 1 hour, 6 hours, 24 hours, 7 days, and 14 days use progressively coarser persisted SQLite buckets and Asia/Shanghai labels.
- Historical dashboard and device trend charts visualize bytes consumed per time bucket, with period upload/download/total summaries. Do not divide persisted bytes by bucket duration or show long-range average speed; instantaneous rates belong only to live connection and current-bandwidth diagnostics.
- Device traffic-path Sankey links also represent accumulated upload plus download bytes for the selected persisted-data range. Persist rule and complete strategy-chain deltas so the path changes with the selected range; never size or label path links with average or instantaneous rates.
- Dashboard exit-mode distribution must use mutually exclusive leaf attribution from persisted complete paths. For example, 节点选择 → 美国 → 美国最佳 → 节点 counts only toward 美国最佳, and any path containing DIRECT counts toward DIRECT. Never chart parent and child policy groups as additive peers; label traffic predating complete-path persistence as 历史未细分.
- Keep the dashboard's opening chrome vertically compact: the dashboard topbar has no descriptive subtitle, and its four primary status cards present label, value, and any short secondary datum on one horizontal line.
- Prefer operational readability over tiny high-density type. Use available card whitespace to keep primary UI text around 12–15 px, headings larger, and auxiliary text at least 11 px; preserve compact component heights unless larger text causes clipping.
- Remove explanatory microcopy when the title, control, or data already conveys the same meaning. Preserve only operational context needed to interpret or act on data, such as IPs, time ranges, units, rule matches, strategy chains, latency, availability, refresh/error state, and safety-critical form guidance.
- Do not render affordances that imply unavailable actions. The topbar account identity is static while theme and logout remain separate controls; do not add a dropdown arrow unless a real account menu is implemented.
- Keep the primary navigation in this exact order and wording: 状态概览、连接统计、流量分析、分流策略、规则管理、订阅管理、网关设置、用户管理. Viewer accounts may access only 状态概览、连接统计、流量分析、订阅管理; enforce that boundary in both navigation/routing and server APIs, while administrators retain all eight workspaces.
- Treat that navigation as three task groups without adding noisy group labels: 观测（状态概览、连接统计、流量分析）、控制（分流策略、规则管理）和管理（订阅管理、网关设置、用户管理）. Keep one page registry as the source of truth for labels, order, permissions and desktop/mobile navigation; subtle spacing may communicate the groups.
- Device analysis is a contextual child of the observability pages, not a ninth primary navigation item. Give it durable URL state so refresh, back navigation and sharing preserve the selected device, and keep connection details as an overlay that preserves the current list filters.
- Use one observability range vocabulary across the dashboard, global traffic analysis, and per-device analysis: live (15 minutes), 1 hour, 6 hours, 24 hours, 7 days, 14 days, and the current calendar month. Every visible range control must issue a real persisted-data query; aggregate more coarsely as the range grows and clearly distinguish the always-live connection path from period-based device charts and destinations.
- Treat the natural calendar month in `Asia/Shanghai` as the primary traffic accounting/reset cycle. Keep high-frequency raw/detail samples for the configured short retention window, increment durable per-device/per-chain and per-device/per-service daily rollups before pruning, retain total-traffic rollups indefinitely, and keep service/host daily detail for at least 400 days so monthly, yearly, and lifetime totals survive panel restarts and raw cleanup without unbounded detail growth.
- The real-time connections workspace follows a dense Surge-inspired operational table: independently scrollable rows, sticky headers and footer, compact zebra striping, status dots, protocol color tags, functional search/device/protocol filters, pause/resume, and density control. Preserve full device, rule, strategy-chain, and termination actions.
- The connection workspace is named 连接统计 and combines active sessions with persisted historical sessions. Provide active/history/all modes, real range filters through 30 days, source-device scoping, accumulated per-session traffic, and Asia/Shanghai start/end times. Keep connection-session rows for 30 days before database cleanup.
- Keep destructive row actions out of the real-time connection table. A row click opens precise connection facts; a right click opens the contextual action menu for connection details, device history, rule creation, and (for administrators) termination. Show cumulative per-connection traffic in the table instead of a redundant action column.
- Device request tracing is host-level and period-aware: retain up/down/total bytes per source device and destination hostname/IP, expose substantially more than a small top-eight list, and make it scrollable. Do not claim full HTTPS URL-path visibility without an explicit MITM capability; ordinary mihomo metadata exposes the hostname/IP, port, rule, and chain, not encrypted paths.
- The favicon/launcher mark uses the existing blue rounded-square brand with a three-layer white routing stack; keep favicon variants deterministic and legible at 16 px.
- The NAS host itself is transparently captured by mihomo TUN: keep `auto-route`, `auto-redirect`, DNS hijack, and `strict-route` enabled, point the host resolver at the TUN DNS peer, and preserve explicit LAN/Docker/ZeroTier route exclusions so management access and mihomo's own egress do not loop.
- Responsive behavior is a first-class product surface. Desktop keeps the full sidebar, tablets use a compact icon rail with two-column content where useful, and phones use a horizontally scrollable bottom navigation with safe-area padding. Remove all global desktop minimum widths; keep touch targets at least 44 px, turn connection statistics into touch-operable cards, expose every right-click action through a visible mobile action button, stack dense workspaces deliberately, and contain genuinely wide data inside labeled horizontal scrollers instead of overflowing the viewport.
- Keep runtime statistics, persistent operational events, and device naming inside the existing 网关设置 workspace as three tabs; do not add another primary navigation item. Runtime accounting groups durable traffic by access mode and actual exit node, with expandable upload/download, current-rate, peak-rate, device, and active-connection facts. Persist meaningful gateway, policy, rule, subscription, and mihomo warning/error events in SQLite, deduplicate noisy core logs, retain them for a configurable period, and present searchable severity filters that remain usable on phones.
